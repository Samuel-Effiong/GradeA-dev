## What I checked by reading
- **The change itself, at the tip.** In each of the six individual-plan functions the call `wallet = lock_wallet_first(wallet)` sits right after the wallet is obtained and before the first bucket query; before it, each function takes only the user-subscription row where it takes one (`activate_subscription` creates the subscription row first, the other three read it under `select_for_update`): the order is subscription row, then wallet, then bucket. All six are `@transaction.atomic`. In the licence helper the call is the first statement of the body. A static pass over each of the six functions found no bucket lock, bucket write or other lock statement before the call.
- **Every caller of the helper.** `_rollover_and_grant_monthly_bucket` has three callers in `billing/license_service.py` (the licence renewal, the offline renewal and `_refresh_teacher_credits`); I found no other. Each holds the licence row (the refresh updates it) and no bucket lock when it calls; the callers' later `wallet.save` uses `update_fields=["overage_blocks_used", "updated_at"]`, so their older in-memory wallet cannot write stale values back over the locked copy.
- **No other function that locks a bucket first and then writes the wallet.** I searched every tracked `.py` file outside tests for `select_for_update` on buckets and wallets: the other bucket-locking sites are `consume_credits` and the refund and dispute paths (all take the wallet first), `expire_bucket` (bucket lock, a ledger row, a bucket update), `expire_trial` (bucket lock, a ledger row, a bucket update) and the code the row changes. I found no foreign key from the ledger to the wallet in the models, so those two write nothing that needs the wallet row; the author gives the same reading in DESIGN.md. They are untouched by this row.
- **The early return.** `process_mid_cycle_credit_grant` takes the wallet lock before its "no longer due" re-check, so an overlapping second run now queues on the wallet as well as on the subscription row. It waits on the subscription row first (the same first lock for both), so the order is the same for both runs; harmless by reading.
- **The author's gate logs, from the commit:** step 0 on the old code, first gate `Ran 9`, `FAILED (failures=9)`, each a real deadlock; fresh gate `Ran 11`, `FAILED (failures=11)` (nine deadlocks, two order tests red because the base never calls the helper); modules and guards `Ran 589 OK` then `Ran 591 OK`; the ten mutants of the fresh gate: 10 KILLED in `mutation_results_5286ccea.json`; billing app `Ran 2141 OK`, 0 FAIL or ERROR. Each log has one Ran line.

## Notes (not blocking)
- **N1. My test reads the order of the statements in one transaction; it does not wait on a lock or find a deadlock.** It shows that the wallet row is locked first in each of the ten paths, and that a late or missing lock is caught. That a charge then cannot deadlock with them is the author's real-thread claim (nine real `deadlock detected` errors on the old code, none on the new, in his logs); I read his Ran lines and did not run his module.
- **N2. The six individual-plan functions now work on a locked copy of the wallet, not on the caller's.** A caller that had `user.credit_wallet` cached keeps a copy that the function no longer updates in memory (for example `overage_blocks_used` is reset on the locked copy and saved). The callers I read (the two conversion call sites in `billing/stripe_service.py`, which go on to record the transaction from the user and the subscription) do not read that cached wallet after the call; I did not read every caller of the other four. By reading only; no test of mine covers a caller's cached copy.
- **N3. Not covered by this row, said by the author and read by me:** `_enroll_teacher_internal` (it reads the monthly bucket without a lock and writes later: no bucket lock for a charge to wait on, but a rollover computed from an unlocked read; a smaller separate fault), `expire_bucket` and `expire_trial` (a bucket lock and a ledger row, no wallet write). My test does not touch them.
- **N4. The order is subscription row, then wallet, then bucket, for the individual paths; licence row, then wallet, then bucket, for the licence paths.** Whether another path takes a wallet and then a subscription or licence row (the charge side's licence-row update is H-182, stacked on this row) is not examined here. Rows 1 to 3 of the order are the author's design and the Senior Manager's rule.
- **N5. Production behaviour is unseen:** the connection pooler in transaction mode, a role's lock timeout, and the foreign-key wait at commit are Postgres behaviour the tests show or do not show; nothing was looked at on a service or in stored data.
- **N6. Not done:** no run of the author's real-thread module, gate, mutants or billing regression (his, once); no pg_locks or pg_stat_activity probe (my method reads the statement order instead); no whole-tree credential scan (the change is four files; the hooks' secrets check passed).
