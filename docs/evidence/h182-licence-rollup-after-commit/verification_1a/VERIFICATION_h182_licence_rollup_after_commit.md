## Notes (not blocking)
- **N1. A charge for a licensed teacher now waits, after it has committed, for the licence row.** My test C shows it: while another connection holds the licence row the charge call does not return (it was still running after 1.2 seconds), although the charge is committed and holds no wallet or bucket lock. In production the call is a grading task or a refund; it returns only when the licence row is free, which for a school-wide renewal is as long as the renewal holds it (the author's H-183). If a database lock timeout is set the roll-up fails, is logged (the figure is short by that amount) and the call returns; with none set it waits. Nothing deadlocks; the cost is latency and a held connection for the teachers of a school during its renewal.
- **N2. The figure can now be short, silently, in two ways the old code could not:** a process that dies between the commit and the callback (the author's stated limit; the exact-once version is Epic B's), and a refund whose charge's roll-up has not yet run, in another process: the clamp at zero then hides the pair, so the figure ends short by that charge (the author's hand-over names it; I read it, I did not test it). The figure only caps a new teacher's first-month grant, so both err in the customer's favour by at most part of one allocation. Beta has no metric counter; the ERROR log line is the count.
- **N3. The rolled-back-charge guard is isolated only by a write outside the transaction.** The author's own rolled-back test is green on the old code by design. My B1 is the same property and only my Z6 fails it; it guards against a future "move the update to another thread or connection" and nothing else.
- **N4. Callers not enumerated, said by the author and not checked by me:** a direct `AIProcessor(...)` construction, and the other call sites outside `ai_processor`. Every charge, wherever it is made, registers its roll-up with `on_commit`; inside someone else's long transaction the roll-up runs at that transaction's end.
