## What production allows today (by reading)
- **Who switches a verified user off:** only the Django admin: the bulk action "Mark selected users as inactive" (users/admin.py 100-105, a `queryset.update`) and the admin edit form (users/admin.py 44). No API, no school-admin or teacher action, no account deletion, no lock-out, no licence-seat revoke sets a user's `is_active` False (those switch subscription or allocation rows). Nothing sets `email_verified_at` back to None. So the verified-and-inactive accounts that exist are those a super admin switched off in the admin.
- **Three roads let such a person back in with only their mailbox:** (1) `POST /auth/otp` VERIFY_EMAIL refuses only "verified AND active", so the switched-off person is mailed an activation code and `POST /auth/verify` sets `is_active` True and returns tokens (no check of the row's state). (2) `POST /auth/otp` RESET_PASSWORD and `POST /auth/reset-password`: a code is made and mailed, the reset sets the person's chosen password and answers 200 with tokens (the tokens are refused later because the row stays inactive, but the person is told it worked). (3) Google sign-in already refuses them (its written carve-out, users/views.py ~1980-2010).
- **"Stays signed in": good news, in plain words.** A switched-off account's existing tokens are refused on its next request and on refresh, because simplejwt 5.5.1 checks `is_active` on every request (`get_user`, CHECK_USER_IS_ACTIVE True) and on refresh. They do not keep working.
- **But the switch-off did not revoke them, only paused them:** the admin bulk action and the edit form did not raise the token epoch (a queryset update; a save with no password change), so tokens issued before a switch-off became valid again the moment the account was switched back on, by any road, for the rest of their life (access 1 day, refresh 2 days, settings 1213-1214). This is the change's second part.

## The change
- users/views.py: (a) VERIFY_EMAIL request: a verified, inactive account gets the neutral 202 an unknown address gets, nothing made or sent; (b) RESET request: any inactive account that passed the never-verified refusal (so a verified one) gets the same neutral 202 before the code row is made; (c) `/auth/verify`: a verified, inactive account is refused through `refuse("Invalid email or token.")` (attempt spent like a wrong guess) before any write; (d) reset step: what is still inactive is verified: `register_failure()` unless already locked, then the generic refusal (no password set, no token).
- users/admin.py: the bulk switch-off is ONE UPDATE: `is_active=False, token_epoch=Case(When(is_active=True, then=F("token_epoch")+1), default=F("token_epoch"))`: only a row active NOW is bumped, once (Postgres reads the row as it was before the statement). `save_model` calls `revoke_all_sessions()` when the form changed `is_active` and the saved value is False (an edit that leaves the flag alone, or switches it on, does not bump). A switch-on never bumps.

### The extra reading before the slot (Senior Manager: "take the extra ten minutes"), what it found
- **A type mix in the bulk UPDATE, fixed before any run.** The first version of the `Case(When(... then=F("token_epoch") + 1), default=F("token_epoch"))` had no `output_field`; the `then` side is an expression over an integer (IntegerField) and the `default` is the column itself (PositiveIntegerField), and Django's mixed-type rule (`_resolve_output_field`: the first source must be an instance of every other source's class) would raise `FieldError: Expression contains mixed types` the first time the admin action ran. The branches are now typed outright (`output_field=IntegerField()`, with a comment saying why); the `mutate.py` anchor (BULK_FULL) was updated to the new text and every mutant was checked to differ from its anchor (none identical).
